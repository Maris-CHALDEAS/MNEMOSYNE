# KiriKiri Web Engine Analysis & Notes

## Overview
KiriKiri Web is a React-based application designed to emulate the desktop KiriKiri engine in the browser (specifically built for the web version of *Fate/stay night*). It provides a robust, timeline-based rendering engine capable of handling complex visual and audio layers.

## Detailed Spec

1. **Interpreter Pipeline (`src/interpreter/`)**
   - **`script-loader.js`**: The entry point for scripts. It fetches the raw `.ks` (KiriKiri script) files over the network (along with a base Macro file) and passes them to the tokenizer. 
   - **`parse/tokenize.js`**: Reads the raw text string and breaks it down into actionable tokens (text, inline tags `[tag]`, full-line tags `@tag`, and comments `;`).
   - **`parse/interpreter.js`**: Takes the tokens and mutates the current `gameState` (handling variables, macros, math logic, and jumps).
   - **`parse/render.js`**: The core of the rendering logic. It takes interpreted tokens and builds a "timeline" of React fragments, breaking the script into sections separated by clicks/waits. It calculates layer opacities, transforms (zooms/pans), and tracks audio triggers.

2. **Reader & Display (`src/reader/`)**
   - **`reader.js`**: The main container view. Holds the `ScrollWatcher`, the text area, and the `Animation` layer.
   - **`scroll/watcher.js` & `detect.js`**: Implements a scrolling timeline view. As the user scrolls down through the generated page segments, `ScrollDetect` components come into view, triggering the corresponding animations and audio for that section.
   - **`animation/`**: Contains the `audio-player` (handling multiple streams of BGM, voices, and SFX) and the `layer` system (which applies CSS transforms, opacities, and z-indexes based on the timeline generated by `render.js`).

3. **Data Generation (`src/resources/`)**
   - Relies on pre-computed indexes like `scene-index.js` and `asset-dictionary.js`. These map scene names and asset hashes, allowing the engine to seamlessly fetch heavy media files on-demand over the network rather than bundling them.

## Codebase Size
- **Total LOC:** ~16,400 lines (including large auto-generated index/dictionary files).
- **Core Engine LOC:** ~4,200 handwritten lines of code (excluding the generated `scene-index.js` and `asset-dictionary.js`).

## Time Estimates
- **Time to Read/Understand Codebase:** ~20 to 30 hours (3 to 4 days) to fully trace and comprehend the state management and rendering math inside `render.js` and `interpreter.js`.
- **Time to Implement Parity in MNEMOSYNE (Solo Dev):** 1.5 to 2 months.
  - **Parser (Tokenizer/Interpreter):** 1.5 - 2 weeks.
  - **Advanced Renderer (Layers/Transforms):** 2 - 3 weeks.
  - **Advanced Audio (Multi-track):** 1 week.
  - **Integration & Polish:** 1 week.

## Navigation Styles (Click-to-Advance vs. Scrolling)
While KiriKiri Web relies on a continuous scrolling timeline to trigger animations and text, traditional Visual Novels typically use a **click-to-advance** model (which MNEMOSYNE currently implements). 
- **Click-to-Advance:** Feels much more like a standard, authentic VN experience. Provides better pacing control for suspense and dialogue delivery.
- **Hybrid Approach:** Supporting both modes as options (a "Classic/Click" mode and a "Read/Scroll" mode) would be the ultimate goal, providing accessibility and catering to different reading preferences. The underlying timeline generation from the script parsing could theoretically feed into either display mode.

### KiriKiri Web Parity — Engine Core
- [ ] **Custom Script Parser (Tokenizer)** — Line-by-line lexer that turns `.mnc` (or similar) plain-text script files into token arrays. Replaces hand-written JS data objects.
- [ ] **Script Interpreter (State Machine)** — Processes tokens sequentially: executes commands immediately, yields/pauses on dialogue lines waiting for user click.
- [ ] **Macro / Template System** — Reusable named blocks of commands that can be defined once and invoked with arguments throughout scripts.
- [ ] **Multi-Layer Rendering** — Support N independent visual layers (background, multiple character sprites, overlays, effects) with per-layer opacity, position, and z-index.
- [ ] **Animation System (CSS Transitions)** — Timeline/keyframe data model. Compile script animation commands into `[{time, opacity, left, top, scale}, ...]` arrays. Apply via CSS `transition` on style changes — browser does all tweening.
- [ ] **Crossfade Transitions** — When a layer's image source changes, render both old (fading out) and new (fading in) simultaneously for smooth blending.
- [ ] **Camera Controls** — Pan, zoom, and shake effects via CSS transforms on layers (`translate`, `scale`).
- [ ] **Path-Based Sprite Movement** — Animate sprites along coordinate paths over time (e.g., character walks from left to center).
- [ ] **Rich Text Formatting** — Inline bold, italic, colored text, and shake/bounce animations within dialogue. (Already on README roadmap.)
- [ ] **Ruby / Furigana Support** — Small annotation text above characters using HTML `<ruby>` tags.
- [ ] **Multi-Track Audio Engine** — Concurrent playback of BGM + Voice + Sound Effects, each with independent volume, fading, and looping.
- [ ] **Audio Fade In/Out** — Smooth volume ramping for BGM transitions and SFX.
- [ ] **Asset Preloading with Abort** — `Promise.race([abort, Promise.all(loads)])` pattern. Preload images/audio for upcoming sections; cancel cleanly if user navigates away.
